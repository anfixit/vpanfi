# Архитектура VPaNfi

## Цель текущего этапа

Репозиторий содержит интерактивный интерфейс продукта и зафиксированный контракт будущих серверных интеграций. Он уже запускается как статическое приложение и позволяет проверить пользовательские сценарии до подключения реальных данных.

## Границы продукта

VPaNfi является самостоятельным продуктом. Он не зависит от Telegram-бота и не использует Cabinet API Bedolaga. Telegram является одним из способов входа и каналом поддержки.

## Целевая схема

```text
Browser
  |
  v
VPaNfi Web / BFF
  |-- Auth service
  |-- Account linking
  |-- Subscription service ---- Remnawave API
  |-- Payment service --------- SBP provider
  |-- Support service --------- Telegram / tickets / AI adapter
  |-- Admin service
  |
PostgreSQL + Redis
```

## Основные сущности

- User: один человек и его профиль.
- Identity: логин/пароль, Яндекс, VK или Telegram. Несколько Identity могут принадлежать одному User.
- Subscription: ровно одна подписка на пользователя.
- DeviceSlot: три базовых места и платные дополнительные места.
- DeviceBinding: устройство, связанное с подпиской.
- Payment: платёж, возврат или пополнение баланса.
- BalanceTransaction: движение средств внутреннего баланса.
- SupportConversation и SupportMessage.
- AuditEvent: критические действия пользователя и администратора.

## Интеграция Remnawave

Интеграция должна находиться только на сервере. Браузер никогда не получает API-токен панели. Адаптер нормализует ответы Remnawave в собственные DTO VPaNfi, чтобы интерфейс не зависел от версии панели.

## Объединение аккаунтов

После входа через новый способ выполняется поиск подтверждённых совпадений по Telegram ID, email и ранее сохранённому внешнему идентификатору. Автоматическое объединение допускается только при криптографически подтверждённом владении обеими учётными записями. Все неоднозначные случаи попадают в очередь администратора.

## Платежи

СБП подключается через отдельный PaymentProvider. Обновление подписки выполняется только после проверенного сервером webhook. Повторный webhook не должен повторно начислять дни, поэтому provider payment id используется как idempotency key.

## Безопасность

- секреты только в переменных окружения или secret manager;
- CSRF-защита для изменяющих запросов;
- rate limiting входа, чата и платежных операций;
- Argon2id для паролей;
- сессии в Secure, HttpOnly, SameSite cookies;
- журналирование действий администраторов;
- запрет прямого доступа браузера к Remnawave;
- минимизация персональных данных;
- резервное копирование PostgreSQL.
